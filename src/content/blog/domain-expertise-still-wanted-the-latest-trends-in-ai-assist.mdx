I keep this one bookmarked because it names something I feel every working day: **the better AI gets at writing code, the more the domain judgment becomes the job.** I lean on AI assistance heavily — most of my recent projects were built with an AI pair at the keyboard — and the article's core claim matches my experience exactly. The model accelerates the typing. It does not supply the judgment about *what is worth typing*.

That judgment is almost always domain-shaped. When I build for the German market, the decisive calls aren't syntax — they're knowing that you can't load Google Fonts from Google's CDN without a consent problem, that a contact form needs a lawful basis and an honest privacy policy, that "just add analytics" quietly becomes a cookie-banner question. On a musician's site the win wasn't the framework; it was knowing that events need the right structured data to show up in search and AI answers. On a translation office's site it was understanding the actual workflow before automating any of it. An AI will happily write all of that code — but only once *someone* has decided it's the right code. That someone is still you.

The part I'd especially point you to is the framing of expertise as **the ability to ask the right question and recognize a wrong answer.** That's the muscle AI doesn't replace and, if anything, makes more valuable: when a tool can produce a confident, plausible, wrong solution in seconds, the person who can smell that it's wrong is worth more, not less. Across a stack that ranges from Astro and Svelte front-ends to Supabase and Cloudflare back-ends to scraping and lead-gen pipelines, the thing that transfers between all of them isn't a language — it's that judgment.

What's changed since I first bookmarked this is that I've stopped keeping that vigilance in my head and started building it into the code. The clearest case is the boost advisor in [Re:Vintage](/work/revintage), which asks a model which Instagram post — if any — is worth putting real ad money behind. The request pins the model to a named tool, so what comes back is a structured object instead of prose to parse. That guarantees the *shape* of the answer and absolutely nothing about its sense, so a second layer runs afterwards: clamp the suggested budget to €3–50 a day, clamp the run to 2–10 days, and drop any recommendation pointing at a post that isn't in the synced data. That last check is there because a model will occasionally recommend boosting a post that does not exist. Forcing the tool call solves parsing; it does nothing about trust. Treating those as one problem is how you end up spending money on a hallucination.

The flip side is that the domain knowledge isn't always mine, and pretending otherwise is its own failure. Tagging [a music library](/blog/beets-assumes-albums), I hit a wall where Last.fm simply had no data for a lot of Turkish and other non-Anglophone artists. So I handed a subagent the library's own commands and let it assign genres. It didn't flatten everything into one "Turkish" bucket — it separated Anadolu Rock from Turkish Indie from Turkish Folk Rock, which is a distinction I'd have wanted and wouldn't have bothered to make by hand. More usefully, it declined to guess on the artists it didn't recognise. That's the version I've come to trust: not a model that knows everything, but one that knows the edge of what it knows. The judgment I kept wasn't "do I know more than the model" — it was knowing which slice of the problem I could hand over, and being able to check the result afterwards.

And the confidently wrong answer doesn't only come from a model. I recently found [three silent bugs](/blog/mock-richer-than-the-api) that a 139-case test suite had been reporting as fine for weeks, because a mock returned richer data than the real API could ever produce. Green output, wrong reality — the same failure mode, from a tool with no intelligence in it at all. Which is the part I'd underline: the skill isn't AI-specific. It's the habit of asking what a confident answer would look like if it were wrong, and going to check.

It provoked a small reframe for me: I've stopped thinking of AI as a junior developer I delegate to, and started treating it as a very fast, very well-read collaborator who has never actually shipped anything to my users. It knows everything and is accountable for nothing. The accountability — the domain, the users, the consequences — stays with me. That's not a limitation of the tools; it's the part of the work that was always the point. Worth a read if you're figuring out where you add value in an AI-assisted workflow.
