## Problem

A working prototype that scraped Trendyol / Hepsiburada / Google Maps for
seller leads, but stuck in "demo on localhost" territory: SQLite file,
hand-rolled JWT auth, no payments, no deploy story, fragile scrapers.
The owner needed it to become a real, sellable SaaS in Turkey.

## Build

Joined as a collaborator and led the rebuild end-to-end:

- **Data layer:** migrated SQLite → Supabase Postgres behind a
  sqlite3-compatible `psycopg` shim, so the ~155 existing call sites kept
  working unchanged.
- **Auth:** retired the local JWT login; trust **Supabase Auth ES256
  tokens** via JWKS, onboard team members through the Supabase Admin API,
  email confirmation flow through Supabase + Resend custom SMTP.
- **Payments:** recurring iyzico subscriptions in TRY (Stripe doesn't
  onboard Turkish businesses). The three tiers live on the server, so the
  browser sends only a tier id; quota resets lazily on read instead of by
  a scheduler; the webhook rejects anything unsigned. A review pass caught
  that an earlier version of that check failed open.
- **AI Site Analysis:** OpenRouter-fronted LLM call with model fallbacks
  (Claude Sonnet 4.6 → GPT-4o-mini → Gemini), produces a 0–100 site
  score, strengths/weaknesses, a call-opener, and a pre-drafted outreach
  email. Signals are first extracted from the HTML by plain code and
  handed over as verified facts, the page text is wrapped as untrusted
  data, and the model is told not to invent speed, traffic or revenue. A
  second pass rewrites the email into native Turkish and keeps the
  original if it fails. A person reviews before anything is sent.
- **Sources:** after launch the local-business search moved from a
  browser scraper to a paid business-data API. In my test it returned
  five enriched businesses in about 3.5 seconds, where the browser path
  took about seven seconds per business and found no email address. Each
  tenant brings its own API key, because a shared key would spend one
  account's quota for everyone; the scraper stays as the no-key fallback.
  A public registry of licensed travel agencies was added as a source.
- **Dedup and provenance:** the same company found in two sources is
  merged only on hard identifiers — tax number, full phone number,
  website domain — never on a similar name. Every field carries a tag for
  where it came from, sources are ranked by trust, and a value somebody
  typed in by hand is never overwritten by a later run.
- **Monitors:** saved searches re-run on a schedule and report only the
  leads that are new since the last run.
- **Outreach guardrails:** an opt-out list with a public unsubscribe
  link, a disclosure footer, a frequency cap and a
  do-not-contact switch on each lead.
- **Frontend:** rebuilt as an Astro + Svelte 5 + Tailwind v4 SPA against
  a Pencil "Data Terminal" handoff. View Transitions for SPA-style
  navigation, persisted rail/banner/toast across nav, dashboard charts
  (funnel, capture trend, coverage, platform mix), team screens for lead
  assignment and per-member performance, an email hub.
- **Deploy:** Dockerized Oracle Cloud Always-Free ARM VM (Frankfurt),
  Caddy for auto-HTTPS, Gunicorn (1 worker × 8 threads — scrapes run as
  in-process daemons), session-persistence volume for headful scrapers
  via xvfb. Wired the app to the owner's existing brand domain at
  `app.digitiva.com.tr` (rather than parking it on a generic Vercel /
  Heroku URL), so the SaaS lives under their established presence.

## Architecture

Decoupled. Flask backend at the repo root (`/api/*`) and the frontend in
its own `frontend/` app. In dev the frontend proxies `/api` → `:5000`;
in prod Caddy serves the Astro `dist/` and reverse-proxies the API on
the same origin. SSRF guard (`safe_fetch`) on every fetched URL.
Pre-deploy security pass: untracked leaked scraper-session JWTs, fixed
Postgres double-quoted SQL literals that were raising `UndefinedColumn`,
plugged a connection-pool leak that drained after ~10 errored requests.

The single Gunicorn worker is a constraint, not a default. Scrape jobs
are threads inside that one process, so a second worker would not see
them, and anything a job holds has to be kept apart per user. The
monitor scheduler follows from the same shape: the container's start
script runs the app's bootstrap in a throwaway process, so the scheduler
starts lazily on the first request instead.

## Reflection

The owner's prototype proved the demand; the rebuild was about earning
the right to charge for it. The most satisfying piece wasn't any one
feature — it was the moment the failing-quietly bugs (pool drain, JWT
sign-out race, post-nav locale flash) stopped, and the app started
behaving like a product instead of a script.

The pool drain is the one I'd tell again. It never showed up as an
error: every page loaded forever, a restart cured it, and then it came
back. A handler that raised before closing its connection leaked one,
and a pool blocks when it is empty, it does not throw. The fix was not
to chase handlers but to return every connection at the end of the
request, whatever happened, and to make closing twice harmless.

Running your own VM has the same quiet character. In October a batch of
vendor security mails made me check the server. None applied, but the
check found the real gap: automatic updates had installed patches for
twenty weeks without ever rebooting into them, and the Docker packages
sat outside their reach. The reboot cost about 25 seconds of downtime.

There are no automated tests. Features were verified with seeded rows
and requests against the API.
